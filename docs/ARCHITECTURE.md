# Forme — Architecture

## North star

The product answers one question: *"What will this garment actually look and
behave like when worn in my size?"* Every architectural decision below exists
to serve that question without either faking the answer or requiring a full
offline cloth-simulation pipeline before the store is usable.

## Stack

- **Next.js 16** (App Router, Turbopack), React 19, TypeScript, Tailwind v4.
- **shadcn/ui on Base UI** (`@base-ui/react`) — not Radix. Compose primitives
  with the `render` prop (`<Button render={<Link href="/x" />}>`), never
  `asChild`.
- **PostgreSQL** via **Prisma 7**. The Prisma 7 config model moved connection
  config out of `schema.prisma` and into `prisma.config.ts` (driver adapter
  `@prisma/adapter-pg`); the generated client lives at
  `src/generated/prisma` (gitignored, regenerated by `npm run db:generate`).
- **Auth.js v5** (JWT sessions, Credentials provider, Prisma adapter).
  Route protection lives in `src/proxy.ts` — Next 16 renamed `middleware.ts`
  to `proxy.ts` and it now runs on the Node.js runtime by default, which is
  why Prisma can be imported there directly (no edge-runtime split needed).
- **Three.js / React Three Fiber / drei** for the 3D viewer, dynamically
  imported (`next/dynamic`, `ssr:false`) so it never lands in the main JS
  bundle for pages that don't need it.
- **Object storage**: an S3-compatible interface (`src/lib/storage`) backed
  by MinIO locally (`docker-compose.yml`), swappable for AWS S3 / Cloudflare
  R2 / Vercel Blob in production without touching call sites.
- **Payments**: a provider-agnostic interface (`src/lib/payments`) with a
  fully functional `mock` provider (default, no keys required) plus real
  Stripe/Paystack/Flutterwave implementations that activate once their
  secret keys are set via `PAYMENT_PROVIDER` + the relevant `*_SECRET_KEY`.

## The 3D asset / simulation split

Real garment cloth simulation (CLO3D, Marvelous Designer, Houdini) is an
offline authoring pipeline, not something a browser — or this coding
session — can run from scratch. Rather than fake it, the schema and viewer
are built around a clean seam between **content** and **behavior**:

```
GarmentAsset
 ├─ baseModelUrl        "procedural:<archetype>" | a real GLB URL
 ├─ fabricMaterialId  →  FabricMaterial (physics: stiffness, damping, drape…)
 ├─ garmentSizes      →  GarmentSize × Mannequin (per-size fit data)
 ├─ animations        →  GarmentAnimation (clip name → duration; clipUrl
 │                        optional — null uses the procedural fallback)
 └─ simulationAssets  →  SimulationAsset (Level 3: precomputed vertex-
                          animation sequences baked offline, for products
                          that get real CLO3D/Marvelous authoring later)
```

**Today** (no real garment assets exist yet), `baseModelUrl` uses the
`procedural:<archetype>` scheme. `src/components/3d/types.ts`'s
`parseModelSource()` is the single place that branches on this — a real GLB
URL takes the `GLTFLoader` path (not yet wired up, since no real assets
exist to load, but the branch and the data model are ready for it).

**Level 1 (Performance Mode) — what's actually running now:**
- `src/components/3d/procedural/humanoid.ts` turns seven body measurements
  into a stack of radial body segments (a tailor's-dummy abstraction, not a
  skinned character — this is a deliberate simplification documented in the
  file itself).
- `src/components/3d/procedural/garment-builder.ts` drapes an archetype
  (tshirt/shirt/trousers/jacket/coat/dress/skirt/jumpsuit) over that rig,
  easing the garment radius outward from the body based on `FitType` so
  cloth never clips through skin.
- `src/components/3d/materials/fabric-material.ts` is a
  `MeshStandardMaterial` with a vertex-displacement shader injected via
  `onBeforeCompile` — the "cloth secondary motion" you see when a garment
  moves. Amplitude and frequency derive from the fabric's `stiffness`,
  `damping`, and `drape` fields, so silk visibly moves more than denim.
- `src/components/3d/hooks/useAnimationController.ts` drives the mannequin's
  root transform and shoulder pivots per-frame (IDLE / TURN_360 / WALK /
  ARM_RAISE / WEIGHT_SHIFT / FABRIC_TEST) — a small hand-built rig, not a
  skeletal animation clip player, though `GarmentAnimation.clipUrl` and the
  `AnimationClip` enum exist so real GLB animation clips can replace this
  per-garment without changing the viewer's public API.

**Level 2 (Enhanced)** and **Level 3 (Cinematic)** are architected
(`SimulationQuality` enum, `SimulationAsset`/`SimulationVariant` models) but
not implemented — there is nothing to consume yet. When real garment assets
exist, `SimulationAsset.sequenceUrl` is where a baked vertex-animation
texture or Alembic-derived sequence would be referenced, and the viewer
would branch on `GarmentAsset.simulationQuality` to pick a playback path
instead of the procedural generator.

## Adaptive performance

`src/components/3d/hooks/usePerformanceTier.ts` does a best-effort device
capability check (CPU cores, device memory, `WEBGL_debug_renderer_info`) to
pick a `RENDER_SETTINGS` tier (LOW/MEDIUM/HIGH/ULTRA: DPR cap, shadows on/off,
antialiasing). `useWebglSupport.ts` gates a full fallback
(`FallbackGallery`) — a static image gallery — for browsers/devices where
WebGL isn't usable at all, so the store never shows a broken canvas.

## Cart & guest identity

Cart identity is resolved server-side (`src/lib/cart.ts`): signed-in users by
`userId`, guests by an httpOnly cookie. That cookie is assigned in
`src/proxy.ts` on every request (Server Components cannot themselves set
cookies — only Route Handlers, Server Actions, and proxy/middleware can), so
`getOrCreateCart()` only ever needs to *read* it.

## Never-trust-the-client boundaries

- Cart line prices are never accepted from the client — `addToCart` resolves
  price and stock from `ProductVariant` server-side.
- Checkout totals (`subtotal`/`shippingTotal`/`taxTotal`/`grandTotal`) are
  computed server-side from the database at order-creation time.
- Payment status is only ever trusted from `Payment.status` in Postgres,
  updated by a provider's `verify()` call or its webhook — never from a URL
  query param alone.
